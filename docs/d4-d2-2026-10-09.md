## D4 acceptance criteria

The three online exchanges in §6.4.1 are implemented for resumed TLS 1.3 proxy
sessions, after WebSocket opening. Fresh pools still need initial OT bootstrap;
this preprocessing is completed before TLS. Prepared sessions finish their
preprocessing before the click. This is a warm-pool protocol guarantee, not a
claim that a device with no OT state can bootstrap in three exchanges.

| Criterion | Implementation and evidence |
| --- | --- |
| ClientHello and key-possession challenge in opening (§6.1) | `ZKFFLOW3` signs nonce, single-use lease, host/ClientHello, declared budget and first Ferret request/reply. Client verifies its key pin before using the reply or sending private HTTP data. |
| Session configuration cannot gate server flight (§6.1) | Warm immediate calls derive proxy/TLS 1.3 configuration from the authenticated host and marker, eliminating the subsequent configuration exchange. |
| Remaining setup overlaps first two flights | Warm Ferret extension starts in Open; its consistency check overlaps TLS. Both VMs await successful completion before using correlations for the proof. |
| One proof flight (§6.5a #2 / #5) | All commitment adjustments, QuickSilver check batches, public claims and attestation request are collected in one bounded mux flight. A drain barrier includes all application streams. Test confirms exactly one underlying write and no pre-release bytes. |
| Attestation is the proof reply (§6.4.1) | Notary verifies schedule, tags, identity, commitments and predicates before signing; replies inside the active mux. No proof-acceptance or close-sync acknowledgment. |
| Three online exchanges | Every measured warm relay run at 33/100 ms has 8 direction changes: one WebSocket upgrade exchange plus three protocol exchanges. Cold bootstrap excluded. |
| No hidden interactive extension | The authenticated declaration is 3,500,000 correlations. Budget overflow fails and burns its lease; a recovery test verifies fresh fallback. Larger circuits can explicitly select `protocolV2: false`. |
| Policy checks before forwarding | The notary validates full ClientHello/SNI and applies admission, destination and DNS/IP policy before forwarding to the origin. |

QuickSilver already used Fiat–Shamir. This implementation binds the complete
public statement and each canonical commitment flush before its check, while
retaining independent ChaCha coefficients. The plan's powers-of-one-field-seed
CPU optimization is intentionally deferred: it changes the degree-dependent
soundness bound and is not needed for one proof flight or three exchanges.
This is a disclosed deviation from that optimization, rather than an unreviewed
change to the check distribution.

Pools remain in process/WASM-instance memory. Disk persistence across restart
and automatic circuit-specific budget prediction are not part of this D4
completion. The conservative budget can increase zero-RTT preprocessing cost.

## Controlled local measurement

M2 Max, release build, local TLS 1.3 `/formats/json` fixture, reveal enabled,
hidden `id >= 1000`. Four warm runs per latency, after one fresh warmup. Final
measurements ran sequentially after builds and hosted tests finished. Milliseconds:

| Phase | FLOW3 0 ms | FLOW3 33 ms | FLOW3 100 ms |
| --- | ---: | ---: | ---: |
| Notary connect | 16.0 | 97.5 | 234.2 |
| Setup | 0.2 | 0.2 | 0.3 |
| TLS | 11.6 | 50.1 | 122.0 |
| Prove | 31.0 | 31.0 | 40.3 |
| Attestation | 30.0 | 66.6 | 135.6 |
| Total | 88.2 | 245.1 | 537.5 |

The prior partial FLOW2 implementation used the same ORIGO schedule: warm
medians were **337.6 ms at 33 ms** and **860.1 ms at 100 ms**. Completing D4
reduces those to **245.1 ms (−27.4%)** and **537.5 ms (−37.5%)**. At zero RTT,
FLOW2 was 69.5 ms versus FLOW3's 88.2 ms; conservative prefill trades some compute
for fewer waits. This is not an isolated D2 performance measurement.

Compared with the full-schedule legacy flow (597.5 / 1489.3 ms), the combined
D4/D2 reduction is 59.0% / 63.9%. Median FLOW3 traffic at 33 ms is 168,335 bytes
up / 613,639 down, **0.75 MiB**, versus legacy's **1.32 MiB**. The fixed prefill
class makes this slightly larger than the previous FLOW2's 0.72 MiB.

The 0→100 ms latency slope is approximately **4.5 RTTs including WebSocket
opening**, versus FLOW2's 7.9 and legacy's 13.6. Removing the one WebSocket
upgrade gives approximately 3.5; compute, framing and scheduling effects make
this an estimate, not an exact message count. The trace's 8 direction changes
and the one-write proof test directly establish the three-exchange flow.

Prove time now contains client proof generation; notary verification appears in
attestation time. Warm Ferret compute is included in connect/preprocessing.
A phase moving towards zero is not by itself a speedup; compare totals.

## D2 remains a separate result

ORIGO's application-key/IV relation is implemented with **16 SHA-256 circuit
compressions versus 32 (−50%)**. Keys, application secrets and downstream outer
HMAC states remain private. Independent native HKDF comparisons and mutated
pad/witness tests pass. See [the security boundary](d4-d2-security.md).

D2 is not fully signed off against Phase 1 of the architecture: direct comparison
against the old VM `Tls13KeySched`, RFC 8448 vectors and independent cryptographic
review remain outstanding. The plan's ~14 estimate also differs from the 16
compressions needed by this implementation's checked keys and IVs. No standalone
D2 end-to-end speedup is claimed here.
