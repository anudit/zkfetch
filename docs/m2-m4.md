# M2–M4 implementation notes

## Runtime and version selection

zkfetch uses a vendored TLSNotary `v0.1.0-alpha.15` (47aee45). Build from the
zkfetch root; its Cargo patches select the vendored crates. Vendored component
tests use their own manifest; HMAC declares its SHA-256 feature explicitly.
The TLS 1.3 transport is implemented alongside TLS 1.2. Validation results
are recorded in the README status checklist.

`zkConfig.tlsVersion` (Rust `tls_version`) accepts `"1.2"`, `"1.3"`, or `"auto"`.
Auto tries TLS 1.3 first and retries TLS 1.2 only for GET, HEAD and OPTIONS.
Other methods make one TLS 1.3 attempt, so a POST is never replayed by fallback.
TLS failures are observed concurrently with HTTP reads, and canceled/failed
sessions abort their driver, prover and HTTP tasks.
Explicit versions never fall back. `res.zk.tlsVersion` records the actual version
and survives session serialization. CLI: `fetch --tls-version 1.3`; playground:
`ZKF_TLS_VERSION=1.3`. Old serialized SDK sessions can omit this metadata.

Only TLS_AES_128_GCM_SHA256 and P-256 key exchange are supported for TLS 1.3.
PSK/resumption, early data, HelloRetryRequest and application key updates are
unsupported. Prover and notary must run the same patched protocol: the new
`MpcTlsConfig.tls_version` and `ProveRequest.predicates` change the wire format.

## TLS 1.3 transport (P2)

The key schedule ports TLSNotary PR #1001 at
`54b0efcd109edb08b01f152e9ba5de3112883e01` to alpha.15's mpz VM. It now lives in
`vendor/tlsn/crates/components/tls13-schedule`. Application key references are
allocated before preprocessing. Key exchange OT setup, record preprocessing and
VM preprocessing/flush run concurrently, matching the TLS 1.2 context tree.
HKDF contexts are assigned once across repeated VM flushes.

The TLS client negotiates a single configured protocol version. In TLS 1.3 it
passes the actual joint P-256 server key and ClientHello/ServerHello hash to the
MPC backend, then the hash through server Finished. Both parties derive
application keys inside the VM. Handshake traffic secrets and application IVs
are decoded to both parties. The prover processes handshake records locally;
the notary does not independently verify the server flight in this transport.

The existing MPC AES-GCM record layer represents the 12-byte XOR nonce as
`iv[0..4] || (iv[4..12] XOR seq)`. Its eight-byte suffix is circuit input, never
an explicit nonce on the TLS 1.3 wire. AAD is the five-byte outer record header.
Deferred received ciphertext is committed before local decryption. Backend
resources and shared OT registrations are released before DEAP finalization.

After commit, the prover discloses inner content types and padding, including
whole non-application records such as session tickets and alerts. Only
application content contributes to HTTP transcript indices. These suffixes
remain untrusted claims until both parties build matching AES-CTR suffix
circuits and QuickSilver authenticates them against the recorded ciphertext.
Suffix circuits precede hash commitment circuits on both peers; allocation
order is part of the protocol. Received GCM tags and closure are checked too.

`CertBinding::V1_3` opens the exact handshake bytes through Certificate and
checks the negotiated version, cipher suite, attested server key share, leaf
certificate and CertificateVerify signature. Offline verification rejects RSA
PKCS#1 v1.5 signatures and a mismatch between binding and attested TLS version.
The signature uses SHA-256 of the handshake with the RFC 8446 server context.
A regression uses a correctly signed attestation with a mismatched TLS version
to ensure the version check is independent of signature rejection.
The certificate chain, hostname, connection time and notary policy are checked
as in TLS 1.2.

The independent `zkf-tls13` handshake and record components remain useful for
reference tests. Their independent server-flight verification is not wired into
the notary. Component tests use real garbling with ideal COT; runtime tests use
TLSNotary's actual MPC, DEAP and QuickSilver path.

This TLS 1.3 design has not received a security review. In particular, review
server-flight binding, public handshake secrets/IVs, suffix authentication and
key schedule transcript hashes before production deployment. No upstream
messages or PRs have been sent.

## QuickSilver predicates (P1, default)

Declare predicates at fetch time with `zkConfig.predicates`. The prover proves
all JSON leaf shapes and requested canonical unsigned-integer comparisons in
the same QuickSilver VM that authenticates plaintext. The notary signs only
verified claims in `zkf.qs.v1`. `present({ prove })` selects a previously attested
claim; it cannot invent a new fetch-time predicate. This avoids a separate
commitment-opening proof at presentation time.

Both backends share authenticated JSON skeleton and path checks. The verifier
requires framing, whitespace, decoded unique keys, quotes, delimiters and
container structure, and binds each claim to the exact scalar range reached by
its dotted path. Duplicate keys, ambiguous framing, noncanonical array indices,
partial scalar reveals and claims outside the body are rejected. Hidden shape
proofs prevent a scalar from smuggling delimiters into the authenticated parse.

`gte` and `gt` target canonical unsigned JSON integers of 1–19 digits.
`gt` becomes `gte(threshold + 1)`, with overflow rejected. Use decimal strings
above JavaScript's safe-integer limit. Fractions, exponents, negatives and
strings are not numeric predicate targets. `expectedPredicates` requires equal
or stronger thresholds and rejects missing claims, including stripped envelopes.
Also pin notary keys and enforce owner/context policy.

## Binius64 predicates (opt-in)

Set `zkConfig.backend: "binius"` at fetch time to add received JSON scalar
commitments `SHA256(payload || 16-byte blinder)`. String payloads exclude quotes.
`present({ prove })` automatically uses the session backend and generates a separate Binius64 ZK proof
and can choose new thresholds after fetching. Binius64 is pinned to
`6a179536d90fcc76eeca0cee4e059f5e17efb459` and uses the ZK wrapper APIs.

The presentation envelope includes the TLSNotary presentation, exact signed
scalar ranges/digests/kinds and the proof. Its public message binding hashes
the domain separator, TLSNotary presentation and claims. The circuit checks
SHA-256 openings, JSON scalar syntax, unsigned parsing and comparison. The
verifier checks signature, identity, openings, signed digests, bounds, overlap
and authenticated paths before accepting the ZK proof.

Both backends expose JSON keys/container structure, scalar byte lengths and
selected values. Binius presentations support at most 128 hidden scalars and
16 KiB hidden payload, with a 32 MiB presentation cap. Larger documents cost
more because every hidden scalar needs a shape proof. The pinned TLSNotary
commitment/blinder serde adapter must be reviewed on dependency upgrades.

## Validation

```sh
bun run build
bun test
bun run typecheck
cargo test --release --locked
cargo clippy --release --locked --workspace --all-targets -- -D warnings
cargo fmt --all --check
# TLS 1.3-only fixture, disclosure, predicates and negative identity checks:
cargo test --release -p zkf-prover --test e2e tls13 -- --nocapture
# Real hosts over explicit TLS 1.2 and 1.3 (no fallback):
ZKF_LIVE=1 bun test packages/sdk/test/e2e.test.ts
```

Vendored TLS 1.3 circuit/identity/schedule tests can be selected from the root:

```sh
cargo test --release --manifest-path vendor/tlsn/Cargo.toml \
  -p tlsn -p tlsn-mpc-tls -p tlsn-tls13-schedule -p tlsn-attestation --lib tls13
```

The Duolingo private streak demo still requires the user's JWT.
Production hosting still needs authenticated WSS, managed keys, a key registry,
challenge issuance and the browser relay.

Validated on 2026-10-07: the final native build passes Bun SDK/CLI tests with
`ZKF_LIVE=1` (five tests, including explicit TLS 1.2 and TLS 1.3 public API
requests and automatic TLS 1.2 fallback). Rust covers TLS 1.3-only disclosure,
QuickSilver and Binius predicates, tampered openings, wrong server keys and
GET fallback/POST non-retry. Vendored tests exercise actual QuickSilver suffix
checks with ideal OT and a correctly signed mismatched-version attestation.
These functional checks do not constitute a cryptographic security review.
